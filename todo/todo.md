> **Baseline: the code is not messy at the syntax level.**
> `flutter analyze` comes back essentially clean — a single unused-element warning (`_DialogField`, `web_users_layout.dart:271`). Naming, formatting, and lint hygiene are solid throughout. That's the fixable, structural kind of "not clean" — not typos or style drift.

## Cross-cutting patterns
*Fix once, applies everywhere*

- [ ] **"Add" screens don't save.** The add-client, add-product (both variants), and the flow feeding sales-order/purchase-order creation all either skip persistence entirely or build the domain object inline in the view rather than through the controller. This is the single most valuable fix in the codebase — it's the difference between demo and working feature.
- [ ] **The same stat-card + sparkline widget is copy-pasted four times** — `categories/web`, `categories/mobile`, `purchase/web`, `users/web` — with only cosmetic renaming between copies (~400 duplicated lines total). Highest-value single dedup.
- [ ] **A "TopBar" widget (search, notifications, quick-action, avatar) is reimplemented per web layout file** in sales, clients, and elsewhere, with every action wired to an empty callback.
- [ ] **Currency/date formatting is hand-rolled 2–3 times per module** instead of using `intl`'s `NumberFormat`/`DateFormat` once — `web_products_layout.dart` is the one file that does this correctly and can serve as the reference.
- [ ] **Filtering and pagination logic consistently lives inside the view's `build()`/`Obx`** rather than as controller getters — true in categories, purchase, users, sales, clients, and stock. Same fix applies everywhere: move to a computed property on the controller.
- [ ] **Mobile and web layouts are built as fully independent files** rather than sharing form widgets or state — visible in categories, products, and purchase. Where only a web layout exists (clients, stock), leftover responsive-breakpoint checks are dead code.
